### Inline decisions
#### 1. Add Step 0 (Discovery)
- **Problem**: In an existing project, generating blank `docs/` files leaves the user with the burden of filling them.
- **Decision**: Added a "Discovery" step where the AI scans the codebase (or asks the user) and auto-fills the docs.
- **Trade-off**: Slightly longer initialization time, but huge time saver overall.

#### 2. Fractal TTE Workflow
- **Problem**: A flat `work/1.0/` directory structure fails when tasks are too large for a single AI prompt.
- **Decision**: Implement Hierarchical Task Networks (HTN). The AI can decompose `work/1.0/` into `work/1.1/` and `work/1.2/`.
- **Trade-off**: More folders created, but cleaner context windows per leaf-node.

#### 3. Model Handoff Pauses
- **Problem**: Using an expensive "Reasoning" model for simple execution tasks wastes tokens and money.
- **Decision**: Imposed mandatory pauses between Think, Task, and Execute phases.
- **Trade-off**: Less "one-shot autonomous" behavior, but much better economic efficiency.

#### 5. Native Language Localization
- **Problem**: Generating English scaffolds forces non-English users to translate them or mix languages.
- **Decision**: Instruct the AI to dynamically translate the generated markdown templates into the user's conversation language during the bootstrap.
- **Trade-off**: Slightly less predictable output depending on the AI's translation, but much better user experience.

#### 6. Directory Encapsulation
- **Problem**: Generating `docs/` and `work/` in the project root can conflict with existing folders or clutter the repo.
- **Decision**: Encapsulate all protocol files within a `.bemyagent/` directory.
- **Trade-off**: An extra folder level, but much cleaner integration into existing projects.

#### 7. Strict Hierarchical Task Nesting
- **Problem**: A flat `work/` directory where all tasks (`1.1/`, `4.1/`, `5.1/`) are at the root level becomes cluttered and unmanageable.
- **Decision**: Enforce a strict hierarchy where tasks are nested inside their Milestone folders (e.g., `work/1/1.1/`).
- **Trade-off**: Deeper folder structure, but much easier for humans to audit and navigate.

#### 8. Semver Versioning Strategy
- **Problem**: The project needs a clear tagging strategy. As a protocol (not a library), standard semver triggers are ambiguous — there are no API contracts to break.
- **Decision**: Adopt semver with protocol-specific semantics:
  - **MAJOR** (X.0.0): Breaking changes that require manual migration of existing `.bemyagent/` setups (e.g., renaming core files, restructuring `docs/` incompatibly).
  - **MINOR** (1.X.0): New features, rules, or structural improvements that are additive and backward-compatible. An agent re-reading the updated `00-ai-rules.md` can adapt without manual intervention.
  - **PATCH** (1.1.X): Bug fixes to protocol rules (ambiguous wording causing agent misbehavior, incorrect path references, typos in instructions).
- **Trade-off**: Semver is designed for APIs, not documentation protocols. The "breaking change" boundary is subjective — we define it as "does a project bootstrapped with vN require manual work to use vN+1?". If yes → MAJOR. If the agent can self-adapt by re-reading the updated rules → MINOR.

#### 9. Contextual DNA Mapping (CDM)
- **Problem**: Tasks in `02_tasks.md` are flat checklists — the agent knows WHAT to do but not HOW to detect failure, WHEN to stop, or WHAT counts as done. The user must mentally reconstruct these criteria during validation.
- **Decision**: During the TASK phase (TTE explosion), embed Drift/Validation/Pivot metadata in each task, scaled by complexity. Simple tasks get no CDM, medium tasks get Validation only, complex tasks get full CDM (Drift + Validation + Pivot).
- **Trade-off**: Slightly denser planning output, but eliminates implicit assumptions and makes human validation faster (criteria are visible, not mental). Complexity threshold to be refined during dogfooding.

#### 10. Symbiotic Validation (VERIFY step)
- **Problem**: CDM defines validation criteria in `02_tasks.md`, but nobody explicitly verifies them after execution. The agent says "done" without self-evaluating. There is an entry gate (Context Saturation Check) but no exit gate.
- **Decision**: Add a fourth step to the workflow — VERIFY (`04_verify.md`). After EXECUTE, the agent evaluates its output against CDM criteria and produces a verdict (PASS / PASS_WITH_CAVEATS / FAIL) before notifying the user. The flow becomes TTEV.
- **Trade-off**: One extra file per validated task, but the cost is marginal (~800 tokens) compared to the risk of having to rollback an entire milestone for an undetected error. Calibration (when to skip, how deep to go) is left to the human-agent pair, not prescribed by the protocol.

#### 11. Documentation Language Rule
- **Problem**: The previous rule ("use the user's preferred language") was ambiguous — it conflated chat interaction language with documentation language. In a public repo with international audience, the user may interact in Italian but need English documentation.
- **Decision**: Documentation language is set at bootstrap time (matching the bootstrap interaction language). It can be overridden at any time with "Set documentation language to [language]". Chat and documentation languages are independent.
- **Trade-off**: Perdo la storicità della motivazione originale per cui era stato introdotto. E' anche vero che ci sono i commit su git per ricostruire eventualmente un po' di storia.

#### 12. Convergence-Based Upgrade Protocol
- **Problem**: How to update BMA in projects already using it? Version-based approaches (version field in settings, changelog) fail because: (a) `settings.json` is generated, so the version must live in `BEMYAGENT.md`, (b) users don't clone this repo (they copy the file or use the website), (c) changelogs require maintaining a separate artifact that grows over time.
- **Decision**: Convergence-based model — the agent reads the new `BEMYAGENT.md` as desired state, compares with the current `.bemyagent/` structure, and generates an `upgrade-plan.md` with a checkbox-based plan. The human reviews and approves before any changes are applied. Protocol files (ai-rules, templates) are overwritable; project files (overview, architecture) get suggestions only. No version field needed — git tags suffice for the repo, the agent determines what to do by comparing states.
- **Trade-off**: Semantic diff is non-deterministic (two agents may produce different plans), mitigated by making protocol files always-overwrite and project files suggestion-only. Token cost of assessment (~100-150 lines overhead) is acceptable vs. the risk of destructive upgrades.

#### 14. Single Slim Template
- **Problem**: `BEMYAGENT.md` (457 lines) is a recurring token cost at every bootstrap/upgrade; the embedded rules cost ~4k tokens at every session restore. The `BEMYAGENT.min.md` experiment proved ~45% compression is viable, but two hand-maintained copies guarantee sync drift (proven by the 2026-06-10 evaluation diff). 
- **Decision**: One file only. Rewrote `BEMYAGENT.md` in compressed style (286 lines, -37%) with a zero-semantic-loss constraint verified mechanically (all 7 settings keys defined in rules, no stale refs, fences balanced). Folded in the evaluation's unambiguous fixes (task table in plan template, `05-decisions-and-issues.md` ref, TTEV naming, Write Gate scope alignment, micro.log tier, secrets redaction, commit-trigger consolidation, role-based model tiers, ADR-per-task in multi-agent mode, `.bak` cleanup). Excluded pending user decision: version pre-filter (Decision 12 stands), self-compression directive for human-facing docs.
- **Trade-off**: Denser text is slightly harder for humans to scan, acceptable for a machine-first bootstrap artifact; human-facing scaffold templates kept readable. A full rewrite is harder to review than patches — mitigated by mechanical verification and the evaluation checklist as reference.

#### 15. Fable.md Cross-Analysis Improvements
- **Problem**: A frontier model's self-authored Operating Manual (`fable.md`) revealed gap areas in BEMYAGENT. Initial analysis identified 5 proposals; critical re-evaluation (prompted by user challenge) found 2 were wrong-context adoptions, 1 was mis-framed.
- **Decision**: 3 surgical additions survived (~75 tokens total). (B) Epistemic labeling rule in §5 — marginal but covers a documented failure mode. (C→reworked) Autonomous rigor principle in §4: in seamless mode the agent IS the quality gate — must be MORE rigorous without a human safety net, self-correct and re-verify rather than wait. (E) User-premise spot-checking in §5. **Reverted**: (A) Intent Alignment Gate — BEMYAGENT tasks arrive pre-scoped from implementation plans; the intent-vs-literal problem is a general-chat concern, not a structured-task concern. (D) Dormancy — creates an escape hatch that undermines the Write Gate; the Micro tier already covers lightweight tasks.
- **Trade-off**: The initial analysis was insufficiently critical — it treated fable.md as an authority rather than unverified input (ironic given fable.md's own §4). Lesson: cross-protocol analysis must evaluate whether the source context (open-ended conversation) maps to the target context (structured task execution). Token cost reduced from ~125 to ~75.

#### 16. Vertical Slicing + Domain Glossary (first measured change)
- **Problem**: Cross-analysis of [mattpocock/skills](https://github.com/mattpocock/skills) surfaced 5 candidate additions. Decision 15's lesson (treat external protocols as unverified input) demanded evidence rather than plausibility, but BEMYAGENT had no way to measure whether a rule works — Decision 13's "~90% compliance" was an estimate, never observed.
- **Decision**: Built an A/B harness (7 sonnet subagent runs on a multi-layer tic-tac-toe fixture: 1 conformance smoke test, 3 baseline, 3 treatment) and shipped only what survived.
  - **P2 — Vertical slicing (§4)**: LANDED ON THE THIRD FORM, after two measured nulls. The HTN had no decomposition *axis*; "too complex" was the sole split trigger, so a layer-at-a-time split was fully protocol-compliant. `baseline-2` produced exactly that failure: one task designing every table for all five features, nothing demoable until three landed together. Three forms were tested across 12 arms:
    1. *Declarative* ("split vertically, never horizontally") — **null**. 23/34 vertical vs 9/15 baseline. Discarded and deleted; the first 3-arm read of 75% was noise and should not have been called "directionally consistent".
    2. *Procedural self-report* (`Layers:` header) — **100% compliance, no behaviour change**. One leaf declared `Layers: [schema, API]` while naming zero files. Discarded.
    3. *Procedural artifact* (`Delivers:` — the one user-visible behaviour this leaf makes work, demoable alone) — **18/18, all genuine end-to-end behaviours, zero implementation steps**. Arms spontaneously surfaced blocking edges ("given a game joined by two seats (2.1)"). LANDED; the declarative sentence was removed as redundant, so net cost is ~1 line.
  - **Instrument bias found late**: the file-path slice classifier scored a leaf "vertical" by counting the files it enumerates — which rewards implementation-list prose, i.e. the horizontal style it was built to detect. It penalised behaviour-written leaves for being written correctly, and read 60→68→75→78% across variants where the real signal was binary. A proxy metric must be checked for bias *against the treatment* before its null is believed.
  - **P3 — Domain glossary (§6 + `01-overview.md`)**: LANDED AND VERIFIED. The first draft produced a glossary in 3/3 runs and a *useful* one in 0/3 — all three contained only pre-existing vocabulary (`game, board, cell, turn, winner`), none the feature's new terms. Populated once at bootstrap, stale immediately. Fixed by moving the maintenance trigger into the §6 `CRITICAL` rule, which already forces same-response updates. Re-run on 3 fresh arms: new-vocabulary coverage went **0/8, 0/8, 0/8 → 7/8, 8/8, 8/8**. Complete separation, large effect. Arms also spontaneously tagged unbuilt terms `— planned` and distinguished `player` (persistent identity) from `seat` (per-game binding) — a distinction the plans depend on.
  - **Rejected**: P1 (fact/decision split — unmeasurable without a human in the loop), P4, P5 (quality gates, wrong axis for a token metric), plus `diagnosing-bugs`, `tdd`/seams, expand–contract, issue-tracker vocabulary (scope or wrong-context).
  - **Blocked-leaf convention (§4 TASK)**: LANDED. Discovered, not reasoned. The same ambiguous requirement produced four defensible handling styles across six runs — withhold `02_tasks.md` and mark the index; write `02` headed `BLOCKED`; write a full plan on a stated assumption with the fragility in CDM Drift/Pivot; or note the block in the task body. All legal under the old rules, and Session Restore had no branch for `02_tasks.md` being absent. Now fixed to one convention: no `02` on a saturation stop, `blocked — [reason]` in the plan index (which restore reads first, so the leaf is never selected as active). **Verified** on 3 fresh arms: every arm where the gate fired followed the convention exactly, with a pointer back to the leaf's `01_think.md`; the arm where it never fired marked nothing (no false positives).
  - **No-BMA control (3 arms, added after the fact)**: the first 16 arms all used BMA, so none of them could say anything about BMA vs not using it. Three control arms got the same fixture and task with no `BEMYAGENT.md` — just "produce a written implementation plan". Results, and they are humbling:
    - **Ambiguity detection: no difference.** 2/3 controls produced an explicit open-questions document; `control-1` listed six holes including the forfeit policy, identity model, and a single-process assumption in its own realtime design. A capable model does this whether or not BMA is present. **The claim "BMA finds more gaps" is not supported.**
    - **Halt behaviour: real but unreliable.** Controls: **0/3** ever stopped — all flagged questions, picked provisional defaults, and built the whole plan on them ("Decisions Made Provisionally… each is implementable as designed"). BMA arms: **3/12** withheld the task plan and marked the milestone `blocked`. So BMA gives ambiguity somewhere to live and *sometimes* converts assume-and-proceed into stop-and-ask — but 9/12 BMA arms also proceeded on assumptions.
    - **The failure mode is real**: `control-3` never listed the forfeit hole at all, silently designing `claim_forfeit` and `end_reason: 'forfeit'` into the schema — inventing a product decision that moves players' ratings.
    - **Cost: BMA is ~2×.** Control ≈52k tokens / 20 tool calls; BMA ≈85k / 47.
  - **What may honestly be claimed**: BMA's reproducible wins are *structural* — 16/16 well-formed workspaces, byte-identical rules regeneration, idempotent self-registration, no blank templates, persistent decision records, resumable state. It does **not** make the model smarter about noticing gaps, and it only sometimes changes what the model does after noticing.
- **Trade-off**: +4 lines to the restore path. The measured cost of a rule is far lower than previously assumed — prompt caching makes recurring reads ~10× cheaper than fresh input, so the "ratchet" concern is real but roughly an order of magnitude smaller than the pre-experiment estimate. The harness itself is the durable asset: it is the eviction mechanism the protocol lacked.

#### 17. UNPOPULATED marker for greenfield bootstrap
- **Problem**: Field report (2026-08-05) — BMA on an empty repo, user answered the bootstrap question with a bare "yes" and no project subject. The agent scaffolded content-empty docs, then reportedly started building instead of documenting when the description finally arrived, risking total loss of project context on session close.
- **Investigation**: 6 arms (3 baseline / 3 fix), 3 turns each, on genuinely empty repos with a neutral prompt. Two of three reasoned fixes were discarded on evidence:
  - **Preamble contradiction (dropped)**: `Do NOT ask permission between steps` (line 6) versus Step 0.3's `STOP and ask` looks like it should suppress the greenfield stop. It doesn't — **6/6 arms stopped and quoted Step 0.3**. The real trigger is an ambiguous affirmative at the next turn: a bare "yes" read as consent, reproducing the blank scaffold **3/3 in baseline, 0/3 with the fix**.
  - **Late-context routing rule (dropped)**: **6/6 arms** wrote the eventually-supplied description into `01-overview.md` (plus `02`/`04`/`05`/`06`) and none started coding. The baseline self-heals because the blank scaffold files `Task 1.1 = "get project description, fill in docs"` into `06-implementation-plan.md` — the instruction sits on disk where the next turn reads it. **The reported data-loss risk did not reproduce.**
  - **UNPOPULATED marker (landed)**: replaces inert `?` placeholders with a greppable signal Session Restore acts on. Unplanned benefit — it tracks *epistemic status per doc*: fix arms cleared the marker on `01-overview` once real content arrived while deliberately keeping it on `02`/`03`/`04` (architecture inferred, no code yet). A `?` cannot express that distinction.
- **Unclosed**: all 3 baselines left breadcrumbs (decision + Known Issue + Task 1.1); the reported agent left none. Divergence unexplained — needs the reporter's model and the wording of their follow-up.
- **Trade-off**: +2 lines. The original recommendation was A+C+D; measurement cut it to C, avoiding 2 lines of permanent restore-path overhead that would have done nothing. Confirms the Decision 16 lesson at a second site: reasoned fixes must be measured, not argued.

#### 18. Milestone convergence gate
- **Problem**: Landscape survey (2026-08, see `drafts/landscape-analysis.md`) of Cline Memory Bank, GitHub Spec-Kit, rtoma's memory-bank protocol, BMAD-METHOD, skill-memory-bank and agentmemory. Nearly everything they do BMA already covers, often better — Lazy Loading beats "read all memory files at start", and the §6 same-response rule beats Cline's manual "update memory bank" command. **One genuine gap**: Symbiotic Validation gates every *leaf*, nothing gates the *milestone*. §6's "tick acceptance criteria as completed" was declarative — the shape Decision 16 measured at zero compliance — so a milestone could close with acceptance criteria no task ever delivered (Spec-Kit's `converge` exists for exactly this).
- **Investigation** — 3 rounds, 15 arms, and the first draft had to be thrown away:
  - **Round 1 (drafted rule, fixture with a fabricated premise)**: **measured harmful.** Baseline **3/3** refused closure — spot-checked the premise per §5/Decision 15, grepped the repo, found no multiplayer code, flagged the missing `01_think`/`03_execute` trail and the copy-paste `04_verify` files. The drafted rule **3/3** dutifully performed the doc-to-doc diff, added the missing task — **and ticked 4 acceptance criteria against a codebase with zero implementation**, because "tick what is met" was read as "tick what the plan claims". It laundered the fraud the baseline caught, and 0/3 spot-checked the premise: the procedure *narrowed* attention. Same trap as `Layers:` one level up — a forced output whose truth isn't self-evident from producing it.
  - **Round 2 (reworded rule, honest fixture — 4 deliverables real, criterion 5 never scoped)**: criterion noticed **6/6** — *detection is not the gap*. What diverged was the action: task created baseline 1/3 vs rule 3/3; milestone kept open 2/3 vs 3/3. `c2base-2` wrote `Status: done (2.1-2.4) — spec gap flagged` — saw the gap and closed anyway. Prose notes aren't actionable state; a later Session Restore reads `done` and moves on. Same shape as the no-BMA controls in Decision 16: **noticing ≠ acting**.
  - **Round 3 (reworded rule vs the round-1 fraudulent fixture — the gating test)**: **laundering 3/3 → 0/3.** All arms reopened or reset the tasks with cited repo evidence, *and* created the missing task. The rewording — tick only with evidence verified in the repo NOW, cited beside the tick, plan status named as claim-not-evidence — repaired the harm without losing the benefit.
- **Decision**: land the reworded gate in §6. Rejected from the survey: `activeContext.md` pointer file (hand-sync drift, already a recorded learning), tracker integration (file-based by design), DB-backed memory (portability is the product), and timestamps-from-`date` (parked — declarative shape, harness can't discriminate it).
- **Trade-off**: +1 line. Round 1 would have shipped a rule that made the protocol *worse* at its most expensive failure; only measurement caught it. Third confirmation that reasoned fixes must be measured — and the first case where the measured verdict was "actively harmful" rather than merely "useless".

#### 19. Greenfield exit condition + no-code-before-overview
- **Problem**: two field reports from the same session (user's contact, opus, English). (a) The agent asked *"do you want me to bootstrap? Explain me what is the project about"* — a permission question the protocol never prescribes, fused with the one it does. The user answered `ok`, and an empty project was scaffolded. (b) Once the user finally described the project, the agent started producing **code** without filling the BMA docs — so closing the conversation would have left code present and documentation absent.
- **Root cause (a)**: Step 0.3 prescribed the *action* ("STOP and ask") but no *exit condition*. An agent that asks, receives `ok`, and considers the question asked is following the text. Four rival behaviours were observed on that ambiguity across 12 arms.
- **Root cause (b)**: the `⚠️ UNPOPULATED` gate lived **only** in §2 Session Restore, so it fires at session start. When bootstrap and the feature request happen in the *same* session — exactly the reported case — it never fires. Decision 17 dismissed this fix after measuring 6/6 arms writing the description correctly, but those arms were in a *bootstrap-incomplete* state with `Task 1.1` pending in the plan, which routed the context. The reported case had bootstrap declared complete. **The test did not cover the reported scenario.**
- **Decision**: two rules. (a) Step 0.3 — keep asking until `01-overview.md`'s opening paragraph can be written without inventing or `?`; create nothing before that. The criterion is tied to an inspectable artifact rather than the agent's judgement that it "understood enough", because an agent biased toward action will settle for "a notes app". (b) §6 — never write code into a project whose `01-overview.md` is unpopulated.
- **Explicitly NOT measured.** The A/B was invalid: subagents refuse coordinator messages on authority grounds regardless of the rule, and directory names leaked the hypothesis (neutral names 1 refusal / 2 proceed; names revealing the gate 3/3 refusals). Consent-shaped rules are not measurable with the harness — see `harness/README.md`. Rule (a) is the **author's design choice** ("an empty scaffold makes no sense"), supported by two mechanical facts found during testing: a half-created `.bemyagent/` makes the next run take the UPGRADE branch against a scaffold that was never populated, and the `UNPOPULATED` path defers the same question at the cost of rewriting six files.
- **Trade-off**: +47 tokens cold. Recorded as a design decision, not an empirical claim — do not cite it as measured.

#### 20. Declarative rule audit + Micro evidence requirement
- **Problem**: Milestones 11/16/18 measured declarative rules at ~zero compliance and procedural ones near-total, but nobody had checked how much of `00-ai-rules.md` is declarative. Two delegated audits (sonnet for classification, opus for redundancy) found **32 procedural (~1456 tok) vs 36 declarative (~1300 tok) — 42% of rule content**.
- **The cut, and what stopped it being bigger**: the redundancy audit proposed deleting 311 tokens. Its own strongest objection killed half of that, correctly:
  - **Handoff Principle (kept)**: judged redundant against the Git rule, but that rule gates on `01`/`02` *existing at commit time* — an agent that executes first and retro-writes the plan passes it, and the artifacts are indistinguishable. It is the only statement of the ordering. 44 tokens against a failure no artifact can detect.
  - **Monthly Audit (moved, not deleted)**: mechanically a human-invoked template, but *"every procedural rule forces an artifact to exist; none checks that it is true"* — it is the only reconciliation mechanism in the file. Moved to `README.md` under human-invoked routines: zero restore cost, capability retained.
  - **`01-overview` unpopulated (kept)**: misclassified as redundant against the §2 grep, which fires *only at restore* — that conditional coverage is precisely the hole Decision 19 closed.
  - **Actually cut (−186 tok)**: three restatements with no observable effect (map-first-then-fragment, "No prose.", prune-before-EXECUTE) plus two non-rules addressing human choices (git-tracking default, §9 dispatch), both relocated to `README.md`.
- **Micro evidence (measured, landed)**: 6 arms on a real reproducible defect (a missing win line). All six fixed it correctly — verified independently by re-running. But **5/6 sized it Micro**, and the Micro tier's `micro.log` format had no evidence field: every one wrote a bare `PASS`. The verdicts were *true* (re-checked) yet unverifiable from the file — each agent had run the tests and reported the result **in chat only**, so it dies with the session. The one arm that went Standard produced a `04_verify.md` with command, literal output (`tests 5, pass 5, fail 0`) and cited diff. Fix: `micro.log` gains an `evidence` field — the command run and its decisive result, never a bare claim.
- **Not landed**: the parallel clause for `04_verify.md` ("paste the command and the decisive lines of its output"). Only 1/3 arms reached that path, so the evidence is 1/3 vs 0/3 — noise by the harness's own criterion. Remains a candidate.
- **Trade-off**: net **−156 tokens** on the restore path despite adding the Micro evidence field. First milestone where the protocol got smaller and stricter at once.

#### 21. Discussion capture
- **Problem**: every write rule in the protocol is triggered by *something happening* — a change, a task, a commit. A long evaluative conversation produces knowledge and triggers nothing, so it stays in the transcript and dies with the session. Observed three times independently: a field report where the project description existed only in chat; Decision 20, where 5/6 arms ran the tests and reported the result in chat while `micro.log` held a bare `PASS`; and this very session, where discussions survived only because they were deliberately written up.
- **Evidence the gap is real, not theoretical**: on this repo's own history, `03_execute.log` carries a *next intended action* in **0 of 10** cases despite §4 mandating it be written *before* executing, and `02_tasks.md` checklists are uniform in **11 of 11** — never mixed states, so never updated during the work. Both are declarative rules about behaviour "during", the category with the worst measured compliance.
- **The failure mechanism, observed directly**: given a pure evaluation prompt with no request to write, baseline arms produced excellent analysis and then closed with *"say the word and I'll write it up there"* — naming the correct destination. The agent knows the rule and knows the file; without an event it asks permission instead of acting, and in a conversation that permission never comes.
- **Decision**: a reply that delivers a verdict, recommendation, or comparison is written to `docs/drafts/<topic>.md` in that same response. The trigger is an event the agent can recognise while producing it — *"I am issuing a verdict"* — not a cadence like "periodically", which is the shape measured at zero.
- **Measured**: writes when needed **1/3 → 3/3**; captures what was ruled out and why **0/1 → 3/3** (the one baseline arm that wrote spontaneously recorded only the conclusion, not the discarded options — the part that prevents re-derivation). Harm arm, a purely factual question with nothing to decide: **0/3** spurious drafts, zero files touched, with two arms reasoning explicitly that a read-only lookup warrants no ceremony. The rule discriminates.
- **Honest caveat**: the primary signal is 1/3 vs 3/3, not the unanimous separation demanded elsewhere in this milestone. It is landed on three converging lines — frequency, quality, and a clean harm arm — not on one decisive measurement.
- **Trade-off**: +83 tokens cold, ~8 warm.

#### 13. Protocol Anchoring Gate (Write Gate)
- **Problem**: During long, technically intense sessions, agents suffer from Recency Bias — the user's immediate request overrides protocol rules read many turns ago. The agent creates ad-hoc files in `.bemyagent/` (e.g., a `crawler_roadmap.md` in `work/`) instead of updating the correct existing file (e.g., `06-implementation-plan.md`). This is model-agnostic: all transformer-based LLMs exhibit this behavior because attention weights on conversational context decay with distance.
- **Decision**: Add a procedural gate (not a declarative rule) in §3 of `00-ai-rules.md`. Before ANY file creation/modification in `docs/` or `work/`, the agent must: (1) re-read the Routing Table, (2) output a `PROTOCOL_CHECK:` line identifying the target file and justification, (3) only then proceed. The forced output creates a token dependency that is structurally hard to skip. The gate exempts normal TTEV workflow writes (appending to `03_execute.log`, writing `04_verify.md`).
- **Trade-off**: ~80 tokens overhead per file creation. Acceptable vs. the cost of orphan files and manual cleanup. Declarative rules were rejected (estimated ~50-60% compliance after 15 turns); procedural gates with forced output estimated at ~90% compliance. Evidence sourced from cross-model analysis (Gemini Pro self-diagnosis, June 2026).

## Engineering Learnings
> **Rule of thumb:** Use this section to capture project-specific patterns, gotchas, or best practices discovered during execution that future agents should know.
- **VERIFY evidence must be mechanical**: Task 9.1's `04_verify.md` claimed "all changes synced to BEMYAGENT.md ✓" (PASS) from recollection; a later diff found 6 divergences. The Anchoring Gate (Decision 13) fixes *where* agents write, not *whether claims are true* — verification claims must come from commands run during VERIFY (diff/grep/test), never memory. Rule now embedded in the template's Symbiotic Validation.
- **Multiple hand-synced copies of the same content always drift**: template↔live rules diverged (pre-Gate sessions); a hand-made `min.md` would have been a third copy. Keep one canonical source per content.
- **Normalise before believing a metric**: the Decision 16 experiment showed treatment 17.4% cheaper on weighted tokens, with *complete separation* across all 3 vs 3 runs (p≈0.05, the lowest achievable at N=3). It was an artifact — treatment also produced 15% fewer lines, and cost-per-line-of-artifact came out 3% apart with fully overlapping ranges. Any efficiency metric must be divided by work done, or "did less" reads as "was faster".
- **A rule can land its artifact and miss its benefit**: P3 produced a glossary in 3/3 runs containing only vocabulary that already existed — the terms worth defining were the new ones. Verify that a new rule changes *behaviour*, not merely that the expected file appears.
- **Declarative rules don't fire; procedural ones do — now measured, not estimated**: Decision 13 asserted this from cross-model analysis (~50-60% vs ~90% compliance) but never observed it. Milestone 11 observed it twice in one experiment. P3 as a declarative sentence: 0/8 new terms across 3 runs. The *same intent*, moved into the §6 `CRITICAL` rule that forces a same-response write: 7-8/8 across 3 runs. P2 as a declarative sentence: no measurable effect across 6 runs. **Where a rule lives matters more than what it says.** When adding a rule, attach it to an existing forced action rather than stating it.
- **A forced output only works when the output IS the deliverable**: the corollary, and the trap. P2's procedural form (`Layers:` header in `02_tasks.md`) hit **100% compliance, 11/11** — and the underlying slicing barely moved (75% vs 60% baseline, not established). One leaf declared `Layers: [schema, API]` while naming zero concrete files. The header is a *claim about* the work; claims are free. P3 succeeded because the glossary **is** the deliverable — you cannot write a glossary containing the new terms without doing the thing. Same principle as the VERIFY-evidence learning above: self-report is not evidence. Force the artifact, never the assertion about it.
- **A procedure can narrow attention — measure for harm, not just for benefit**: Decision 18 round 1. Given a milestone whose "done" records were fabricated, the *unaided* protocol caught the fraud 3/3 (§5 premise spot-check + §4 mechanical evidence). Adding a well-intentioned convergence procedure made it **worse**: 3/3 followed the new steps and ticked criteria against non-existent code, 0/3 spot-checked the premise. A new rule competes for attention with the rules already there. Every candidate needs an arm where it could plausibly *hurt*, not only one where it could help.
- **The §6 CRITICAL rule did not fire on infrastructure changes — observed on myself**: `harness/` was added to this repo (11 files, a Node app, a Python script) without updating `03-code-map.md`, `01-overview.md` or `04-tech-stack.md`, despite §6 mandating those updates "in the SAME response as any change". The drift was found later by running the Monthly Audit against this repo. Likely cause: the rule reads as being about *project code*, and adding a development harness did not register as "a change" — the same ambiguity class as the greenfield exit condition, where an action was prescribed without its trigger being pinned down. Candidate wording: name the trigger as *any file added to or removed from the repo*, not just a code change. Untested — do not land on this reasoning alone.
- **The measuring instrument can inject the noise**: the harness fixture shipped with a native dependency that would not build on current Node. Three arms out of five spent their run diagnosing and working around it; one downgraded its own verdict for lack of a runnable environment. The rule under test was never the hardest thing in the room. Verify the fixture installs and runs before launching any arm.
- **Distinguish a null from an inconclusive**: a null means the rule was tested properly and had no effect — delete it. Inconclusive means the test was invalid and yields no information — change nothing. The Milestone 13.2 inertness run came back 0/3 vs 1/3 (noise by the harness's own N=3 criterion) but with three design faults, so it is inconclusive: the 42% declarative share remains unverified and nothing was pruned. Reporting inconclusive as null would have deleted ~207 tokens of possibly-working rules.
- **Measure the mechanism, not the outcome**: the mechanism check (does the glossary contain the new terms?) resolved decisively at N=3. The downstream token proxy for the same changes never resolved and produced a false positive. Prefer the directly-observable artifact of a rule over its hoped-for downstream effect.

- **The premise spot-check (Decision 15) is robust**: an accidentally-broken fixture — a comment asserting a bug in already-correct code — was caught by **6/6** arms, with and without the other rules under test. Each verified numerically and refused to edit; one noted that "fixing" it would have introduced the very bug described. This is the strongest evidence yet that §5 works, and it arrived by accident.

- **Read delegation — candidate REJECTED, and the reason is not the one the experiment was designed to find** (Milestone 14, 9 arms: baseline / free delegation / bounded pointer-only). Origin was the Portal-by-Spotify article, which is model routing, not a code map. Defect survival showed no separation — FIXED 0/3 baseline, 1/3 free, 1/3 bounded, and 0/9 leaderboards collapsed per playerId — but the count is not the finding. **0/9 arms delegated anything.** Zero `path:line` citations, including 3/3 of the arm whose rule explicitly ordered them to be logged; every keyword hit resolved to either the arms' own architecture prose or the rule text copied verbatim into their generated `00-ai-rules.md`. The trigger was met and visible (`session.js` is 309 lines against a threshold of 200, which arm b's rule named) and capability was confirmed present beforehand. This is the Milestones 11/16/18 declarative null again: a clause granting a permission measures at ~zero compliance, and the "log the citation" forced output failed exactly like the `Layers:` header. A rule nobody exercises is inert text charged at every session restore — it does not land.
- **Agents trust a doc comment over the code it describes** (found incidentally in Milestone 14, and worth more than the question that produced it). `session.js` declares an invariant in a header comment and violates it 40 lines below in a three-line helper. 7/9 arms read the file — wired it, documented its API, one quoted the comment verbatim in its final report — and 9/9 shipped the violation. §5 says "NEVER assume a function, variable, or import exists without seeing it"; it does not say the comment describing them may be lying. This is the same failure the delegation hypothesis predicted for summaries, occurring with no summary involved — which is also why the treatment had nothing to separate from. Needs its own round as a §5 candidate.
- **A cost difference between arms means nothing when the mechanism never fired**: the free-delegation arm came in ~13% cheaper than the bounded one, a number that would read as "delegation saves tokens" in any write-up that quoted it. Nobody delegated. The gap is task variance, and the more expensive arm also wrote the most tests. Third occurrence of the same trap (see Decision 16 and the normalisation rule) — a cost metric must be tied to a mechanism that demonstrably ran before it is allowed to mean anything.
- **Score in batches, and never score the first one**: round 2 was run as three batches of three, one arm per condition. After batch 1 the tally was 2/2 treatment vs 0/1 baseline — clean separation, obvious direction, a publishable story. The final tally over 9 arms was 2/9 with no structure at all. The discipline that saved it was written into `02_tasks.md` before launch, not decided in the moment.

- **The declarative/procedural lever works on tool invocations too — and this narrows the Milestone 14 conclusion** (Milestone 14.6, 6 arms, one Routing Table row, two phrasings). Permissive ("a code graph is available, prefer it over grepping"): **0/3** invocations. Procedural ("run the query first, then read the files it names, log the returned nodes"): **3/3**, with all three citing real nodes the tool had actually returned. Same tool, same task, one line apart. 14.3 concluded that agents do not invoke optional affordances; that was too broad — the barrier was never tool-ness, it was the declarative shape, the same one measured at ~zero in 11/16/18. First demonstration of that lever on something the agent must *run* rather than read or write. Any future rule wanting an agent to execute something must be a Routing Table step, not an available option.
- **Invocation is not value, and the two are easy to conflate**: in the same round, 6/6 arms built the feature on `listOnline()` and shipped equivalent tests, whether they reached it through the graph or by reading the file. The tool changed the route, not the destination. A 3/3 compliance number says the instruction was followed; it says nothing about whether following it helped. The round was designed so tool quality would cancel between conditions — reading the 3/3 as evidence the graph *works* would invert what was measured.
- **A navigation tool cannot be evaluated on a fixture small enough to just read**: the harness fixture is under 500 lines across 8 files, so no graph can beat reading all of it. This is the Milestone 14.1 problem one level up — there the fixture had no file large enough to trigger a read rule, here the whole project is too small for navigation to matter. Measuring whether a code graph earns its place needs a substantially larger fixture, which is a real cost to decide deliberately rather than drift into.

- **The value question for a derived code map is freshness, not retrieval** (reframed in discussion, 2026-10-10, immediately after 14.6). The 14.7 block was written as *"does a graph beat reading the files?"* — that is the **vendor's** value proposition for codebases too large to read, imported from Graphify's framing, and it is not this protocol's pain. Ours is drift: the structural layer of `03-code-map.md` is hand-maintained and 13.7 caught it stale on this repo despite §6's CRITICAL same-response rule. A derived artifact cannot drift. Restated that way the candidate is a tool-agnostic **mechanism** (*"the structural layer MUST be generated, not hand-written"* — ctags, tree-sitter, anything) rather than a product, which also answers the dependency objection, and it is measurable on the **small** fixture: staleness needs a row that lies, not a codebase too big to read. The instrument limit blocks the navigation question only, and the navigation question does not gate adoption.
- **Whether stale prose about code actually costs anything is unresolved, and this repo's own evidence points both ways**: the premise spot-check caught lying prose **6/6** (Decision 15, a comment asserting a bug in correct code — arms verified numerically and refused to edit), while the doc-comment round was fooled by it **9/9** (14.5, an invariant violated 40 lines below its own docstring). Inferring from the two, not measured: the first invited verification because it made a falsifiable claim about behaviour the arm was about to change; the second was background context the arm had no occasion to test. A stale code-map row is the second kind. 14.5 resolves this and gates 14.7 — and **two of its three possible outcomes delete the structural layer rather than generating it**, which is the cheaper result and should not be treated as the disappointing one.
- **The plan file silently becomes a journal, and it sits on the hottest path**: §3 says `01`/`02`/`03` *"MUST hold only logical trees + pointers to fragments — never inline specs or long explanations"*, and `06` is read on **every** write to `docs/` or `work/`. Milestone 14's rows grew to **964 words — 37% of the entire plan file** — by recording findings inline instead of pointing at `05` and `work/`, which already held them. Compressed to 412 words with no loss, since both destinations were already correct. The pull is structural: a row is written at the moment the finding is freshest, when summarising feels like discarding. Check the plan's own size before adding to it — a milestone's rows are an index, and the test is whether each one still fits on a line.
- **A mandated section stays empty only when nothing obvious belongs in it** (Milestone 15.3, 6 arms — corrects the reading of the P3 glossary result). FEDERATION #7(a) proposes a mandatory `## Project rules` section *"even empty, with a guide line"*. I objected that this is the shape measured **0/8** in P3. **It was filled 3/3.** The difference: in P3 the section had to hold vocabulary that **did not yet exist**, so there was nothing to put in it; here an explicit user instruction was sitting in the prompt. The 0/8 result was never about mandated sections — it was about mandating a container for content the agent had no occasion to produce. This is the harness's *"give the rule an occasion to fire"* trap seen from the other side, and it means **every past null must be re-read for whether the occasion was present** before it is treated as a null about the rule.
- **The harness keeps its evidence somewhere volatile — and a verdict outlives its proof** (found 2026-10-22, one day after 15.3 closed). The six arm directories, the setup script and the scorer were all in the scratchpad; it was cleared between sessions. `04_verify.md` still asserts *"scored by reading files on disk"* and that disk is gone, so the 3/3-vs-3/3 cannot be re-checked by anyone, including us. A grep against the vanished path returned empty and **would have been reported as "0/6 arms wrote `04_verify.md`"** — a fabricated finding contradicting our own scorer run the previous day, caught only because the result was implausible enough to check. 14.6 already carried this as a caveat about the 14.3 directories, which makes it systemic. Fix landed in `harness/README.md`: the scorer and its raw output are copied into the tracked `work/<N>/<N.Y>/` before a round is called done. **This is our measuring apparatus failing the rule we impose on everything else** — the same shape as FEDERATION #5 and #7, evidence that evaporates is evidence hidden from whoever must trust the verdict.
- **Kiro (AWS) surveyed 2026-10-22 — tooling, not a peer, and the third vendor to ship a structured spec workflow with no outcome evidence.** GA 2025-11-17, closed source (`kirodotdev/Kiro` is an issue tracker; *"the product source code is not hosted here"*), paid from $20/mo. Spec triple `.kiro/specs/<name>/{requirements,design,tasks}.md` with **EARS** acceptance criteria, property-based tests derived from those criteria (**optional by default**, and completion is marked by inspection rather than a test-pass gate), steering files with conditional inclusion modes. **Fourth independent convergence on ceremony sizing** — but on a different axis: Kiro sizes by the user's felt certainty chosen before anything is known, BMA by blast radius in files touched, which is objective and decidable. Second vendor to move lazy loading into the harness layer. **Publishes no measurement of any kind**, and hedges its one effectiveness claim with *"which we believe"*. Not a competitor: product lock-in rather than a protocol, and a team on mixed tools cannot run it. It also reads `AGENTS.md` natively, so our self-registration already works there unchanged. No protocol change.
- **Kiro run and compared on controlled input, 2026-10-23 — and the headline is that its CLI has no spec flow at all** (`work/15/15.12/`). Kiro CLI 2.33.1, model pinned `claude-sonnet-4.5`, same task text as the six arms in `work/15/15.10/arms/`, clean fixture with no BMA present, 1.85 credits. **(a) The clarifying-questions behaviour is the harness, not the model**: Plan mode asked 3 structured questions (reproduced 2/2), default mode asked 0 on the identical input with cleared context; asked why, it quoted its instruction — *"ask AT MOST THREE structured questions per turn … even for straightforward tasks"* — and volunteered that it would otherwise *"pick sensible defaults and note them as assumptions"*, which is §4's Saturation Check verbatim, and whose default matched 6/6 of our arms. **(b) Neither mode produced a single artifact on disk** — no `.kiro/`, no markdown, no plan; after the Plan run the folder was byte-identical to the restored fixture. The reasoning lives in `~/.kiro/sessions/cli/*.jsonl`, 112 KB, outside the project, unversioned, invisible to a teammate or another tool. **That is Decision 21 confirmed from outside, and FEDERATION #7 observed in a shipped product rather than argued.** Fair caveat: a harness can own state, a protocol cannot, so both choices are coherent — the consequence is still that their reasoning is not portable, reviewable or diffable. **(c) The spec triple is IDE-only**, so it is not scriptable from a terminal, and nothing here measures Kiro's spec-driven capability.
- **FEDERATION #1 measured and REJECTED — the proposed fix would have broken working behaviour** (2026-10-23, 2 arms). The report says a folder holding only `.md` files is *"neither empty workspace nor codebase exists literally"* and proposes `GREENFIELD — no code yet (bootstrap files only)`. Tested on a real documentation-only project (a 227-word support handbook: README, escalation policy, shift handover, one decision record — **zero code**), bootstrap only, no task. **Both arms classified it BROWNFIELD, scanned it, and derived the project from the documents**: `01-overview.md` carries a glossary built from the handbook's own vocabulary (Escalation, Handover note, On-call engineer, P2, Enterprise plan), `05` indexes the handbook's existing decision 0001 by link, and one arm turned a topic named in the README but missing from `docs/` into task 1.1. **Declaring a folder of markdown "empty" would reclassify a real project as absence and throw that away.** The ambiguous wording produces the right answer; the proposed clarification does not. Withdrawn before it landed. **Still untested, and possibly the reporter's actual case:** a folder containing only BMA's *own* bootstrap files — `BEMYAGENT.md` alone, or a half-written scaffold — which is a different question from a folder of real documents.
- **FEDERATION #8's merge algorithm REJECTED — on Decision 12's own reasoning** (2026-10-26). The report proposed diffing against the base version and merging local lines before overwriting `00-ai-rules.md`. Decision 12's trade-off section already anticipated this: *"Semantic diff is non-deterministic (two agents may produce different plans), **mitigated by making protocol files always-overwrite**."* A merge step **reintroduces exactly the non-determinism that decision mitigated**, and it does so inside the one operation where a wrong guess silently corrupts the rules the agent is about to obey. The loss is already addressed without it: UPGRADE now states that protocol files are overwritten and that customisation belongs in project files, and CLEANUP keeps the `.bak` of anything that changed — so the lines are recoverable and the user is warned before, not after. Accepting the report's diagnosis does not oblige us to accept its remedy.
- **A cadence is not a trigger — now measured twice, on two different rules** (Milestone 16.1, 9 arms, two-turn). Issue #3 proposed a conversation log appended every turn. **0 of 9 logs contain the second turn.** Four logs exist; each holds a single entry for turn 1, 1-3 lines, created at bootstrap and then abandoned. This is `03_execute.log`'s next-intended-action failure reproduced in a fresh rule: that one mandates a per-turn write and carries it in **0 of 10** cases on this repo's history. Two independent per-turn rules, both at zero. **Decision 21 works because its trigger is an event the agent recognises while producing it (*"I am issuing a verdict"*); a per-turn cadence has no such event, and no wording fixes that.**
- **The per-turn write belongs in a hook, not in the protocol — demonstrated, not argued** (16.2, after 16.1 measured the prose form at 0/9). A `UserPromptSubmit` hook appends each prompt to `.bemyagent/log/YYYY-MM-DD.md` **before the model sees it**. Pipe-tested with newlines, quotes, backticks and `$(whoami)` — preserved verbatim, and `$(whoami)` stayed literal because the text reaches the file through `jq` and never through shell evaluation. Then confirmed live: the user's message was in the file before this session read it. **Both of 16.1's failures are properties of asking a model to remember**, and neither survives when nothing is asked of it. It also beats the form that survived 16.1 — *declare where the harness keeps its transcript* accepts the harness's format outside the repo, while a hook writes the file issue #3 actually describes, in the repo, in a format we choose.
- **The protocol's ceiling, now named: anything that must happen *before* or *on every* X cannot be a prose rule.** Two rounds and eighteen arms to measure that at zero. The answer was never a better wording, it was the wrong layer — a markdown file intercepts nothing. Same boundary found against Kiro in 15.12, where their permission gates block and ours only speak; `PROTOCOL_CHECK` is the ceiling of what prose can do. **BMA cannot ship the hook**: it can specify the contract (where the file lives, what shape it has, how the distilled files cite it) and leave each harness to fill it, which is the algorithm-not-script pattern again — *specify what must be true, not how it is produced*. A harness without hooks gets nothing, and that cost must be stated rather than hidden.
- **Issue #3 LANDED as a contract, on a judgement the evidence could not make** (16.4, owner's call 2026-10-27). The measured position was: problem real at 7/9, remedy dead at 0/9, mechanism proved by hook, **and no evidence anyone reads the file** — so the recommendation was to add nothing. The owner overruled that, and the reasoning corrects a category error on this side: **the log is insurance, not a tool.** A smoke detector is not judged by how often it goes off. *Invocation ≠ value* (14.6) was about a tool changing the agent's work; this is not meant to change the agent's work at all, it is meant to be there for the **human** when something goes wrong — which is also the strongest reading of **guarantee 3**, *hide no information and no reasoning*. A raw record of the user's own words is the purest form of that, and nobody reading it does not weaken it.
- **What landed, and what deliberately did not** (+4 lines): a `conversationLog` field in `settings.json` (`""` = off, per guarantee 2), a Routing Table row, and a contract stating that **the protocol does not write it** — naming both measured failures inline so nobody re-proposes them: a per-turn append measures ~0, and an agent asked to quote verbatim paraphrases. The harness writes it or nothing does; where none can, the folder stays empty and costs nothing. Entries are **cited** rather than copied into THINK and decisions, which is a substitution and not a new obligation. Never read at Session Restore.
- **Honest label on this one**: it is landed on a judgement about human value that this harness **cannot measure** — the same class as the consent rules parked as unmeasurable, not the same class as the rules carrying an A/B behind them. Recorded as such rather than dressed as evidence.
- **The problem issue #3 names is real and larger than reported: 7 of 9 arms lost the correction entirely** (same round). The second turn asked to drop a field and skip a test — a request that changed the work, altered three test assertions and updated the code map, **and left no durable trace anywhere in the repo** in 7 of 9 arms. The two that captured it did so by accident of where they were already writing (`03_execute.log` in one, `micro.log` in the other), which is not a mechanism anyone can rely on. **The problem stands even though the proposed remedy failed**, and it should not be filed away with the rejection.
- **Told to write verbatim, the agent summarised — the objection caught live** (same round). b-1 was the only arm in the verbatim condition to write anything. Its entire log line: *"Turn: wire session.js into index.js (POST /api/sessions, GET /api/online)"*. The user's message was four clauses and said none of that. **A "verbatim" record written by the agent is a reconstruction wearing the label of a transcript**, which is worse than no record: a disagreement checked against it would be checked against something the user never said. Visible only by reading the file — the scorer had counted it as written. Summary form also beat verbatim on creation, **3/3 vs 1/3**, and a summary at least does not claim a fidelity it lacks.
- **Issue #3 rejected in the form proposed; the surviving candidate is to declare where the harness's transcript already lives.** One `settings.json` field, no write rule, no cadence to forget — **the harness writes it whether the agent remembers or not**. It abandons projects whose harness keeps no transcript, which is a real cost. Note the symmetry with 15.12: Kiro's transcript exists precisely *because* the harness writes it; our criticism was that it sits outside the repo, never that the mechanism was wrong.
- **The method proposal landed, deliberately as a norm and not a gate** (FEDERATION, the item worth more than the eleven). §4 now says: *"the author checking their own work is the weakest available check — it re-runs the reasoning that produced the error. Where a second agent or model is available, have VERIFY run by one that did not do the work … Where it is not, say so in `04_verify.md` rather than implying independence."* Requiring it would exclude anyone without a second model, which guarantee 1 forbids; stating the asymmetry costs nothing and the fallback clause makes the absence visible instead of silent. Our own harness has always been this, unwritten — and the 2026-10-20 survey supplied the second argument: **every measurement in this project's history ran on one harness and one model family.**
- **#4 resolved by the evidence rather than by an exception** (2026-10-23 greenfield arms, closed 2026-10-26). The report asked for an explicit exception to §3 for documentation-only projects — the shape Decision 15 rejected as Dormancy. Unnecessary: both arms adapted `03-code-map.md` to a repo with no code on their own, one writing *"No code. Handbook content map"* with a clean file→content table. **But arm-2 dragged the code-shaped sections along and filled them with `n/a`**, which is the real friction the report felt. So the fix is not an exception, it is naming what the limit protects: *"The limit protects the restore path, not a fixed shape: keep the sections the project actually has and drop the rest — a repo with no code gets a content map of its documents, not a code map full of `n/a`."*
- **#5 and #9 accepted in principle, deferred to rounds — and the reply says so rather than implying they shipped.** #5 (`PROTOCOL_CHECK` leaves no trace) is guarantee 3 and the principle is settled, but the form costs a write per file touched and Decision 18 requires an arm where it could plausibly hurt. #9 (state needed to resume must live outside the session) is a rule we **already have and already measured at 0/10**, so landing the report's wording would change nothing; what is new is the trigger, and 14.6 showed trigger shape does move behaviour — which is a reason to measure it, not to skip measuring.
- **This is the strongest evidence yet that documentation-only projects are a core use case, not an edge case** (same round, bearing on FEDERATION #4). The protocol did real work on a repo with no code at all: derived vocabulary, cross-referenced an existing decision, and found a gap in the handbook worth a task. Which makes §3's *"`01`/`02`/`03` hold only logical trees + pointers"* actively wrong there — for that project the tables **are** the content, and #4 says so. The round did not test §3, but it removes any doubt about whether the case is worth serving.
- **An unanchored grep for `UNPOPULATED` self-matched the rule that defines it** — while checking whether either arm had taken the greenfield branch, the only hit was `00-ai-rules.md` itself. §2 warns about exactly this (*"anchoring matters: an unanchored search self-matches this very rule"*), and the warning earned itself inside five minutes of being read.
- **Their gates block; ours only speak — and a markdown file cannot close that gap** (same run). Kiro stopped three times for approval, with four-level granularity (specific path / directory / entire tool; exact command / partial / base / entire tool). Our Write Gate emits a `PROTOCOL_CHECK:` line: a **self-report that can prevent nothing**. Decision 13 landed it for *where agents write*, measured on compliance, and it works for that — but it has never been able to stop anything, and this is the first time the limit has been written down next to a working counter-example. Same distinction the 2026-10-20 survey drew about `skills-constitution`'s `--strict`. Structural, not fixable in prose.
- **Our VERIFY evidence rule is a citation rule, not a coverage rule** (Kiro survey, and it is the sharpest external criticism received so far). §4 demands evidence from commands run during VERIFY and never from recollection — but says nothing about the command **touching the change**. `npm test` over a suite that never exercises the modified path yields a PASS with a valid citation and zero information. Kiro derives its tests *from the acceptance criterion itself*, so it ties evidence to the claim in a way we do not; it then makes them optional, which we do not. **Each of us has the half the other lacks.** This is weakest exactly where the protocol claims its strongest differentiator, and it is not written down anywhere else.
- **EARS would be a schema constraint, not a wording change — correcting how this project classified it.** The RFC-2119-style proposals were dismissed here on the grounds that Decision 16 measured wording strength as not moving compliance. EARS is a different thing: `WHEN <condition> THE SYSTEM SHALL <observable>` makes an unverifiable criterion **syntactically impossible to state** — you cannot write *"the code is clean"* in that form. That is a mechanism acting on artifact content, which sits on the forced-artifact side of our own measured line, not the adjective side. Untested, and by our own rule it needs a round before it lands.
- **EARS measured: INCONCLUSIVE, and the fault was the task, not the rule** (Milestone 15.10, 6 arms + 4 burned on a voided first round). FORM separated cleanly — 0/3 baseline vs 3/3 treatment — but that only confirms the clause applied; the CDM names counting it as success as Drift. Both real measures sat at the **ceiling in the baseline**: CITATION 3/3 vs 3/3, COVERAGE 3/3 vs 3/3, because every arm added its own test file so every cited `npm test` covered the change. The task was picked precisely because the shipped suite covers only `rules.js`, making an uncovered citation *possible* — **competent agents simply did not take the opportunity to fail.** A ceiling in the baseline is a finding about the task, not about the rule. By the 13.2 distinction this is inconclusive, not null: change nothing, land nothing, reject nothing.
- **A round can be killed by choosing a task on the ceremony boundary** (15.10 round 1, voided). The task was *"an out-of-range cell crashes, return 400"*. Two faults, either fatal: the premise was **false** (it already returned 400 — both arms caught it independently, §5's premise spot-check now ~8/8 across this project, two of those produced by my own error), and the task sat on the Micro/Standard line so **a-1 sized it Standard and b-1 sized it Micro — both correctly**. Micro writes no CDM and no `04_verify.md`, so the rule under test could not fire in half the arms. The Saturation Check had claimed this was covered: it verified that *a Standard task* writes Validation criteria, then chose a task that is not reliably Standard. **Verify the premise, and verify the task's ceremony tier, before spending arms.**
- **What VERIFY does with a criterion may differ from whether it cites a command — observed, not measured** (15.10). Treatment arms discharge criteria one at a time (*"WHEN same playerId posts twice THE SYSTEM SHALL list once: npm test -> '…'"*); baseline arms report an aggregate (*"npm test -> 7 pass 0 fail"*) and then describe what the tests happen to cover. Criterion→evidence versus evidence→description. Separately, one baseline arm's entire Validation criterion was *"npm test passes incl. new tests"* — circular, asserting nothing about the system, and syntactically impossible in EARS form. 1/3 is noise at N=3, so both are mechanism demonstrations, not rates. **The next EARS round should measure criterion quality**, which is what these point at, rather than citation and coverage, which §4 already delivers at ceiling.
- **§6's CRITICAL rule already captures standing user rules — measured, not assumed** (same round). The primary measure was a **null**: the standing rule reached a durable file in **3/3 baseline and 3/3 treatment**, and `05-decisions-and-issues.md` caught it **6/6**. Two of three baseline arms also wrote it into `AGENTS.md` unprompted. So FEDERATION #7(a) does not land — not because the section fails, but because the protocol demonstrably has the capability already, and the section would add lines to the file read at every restore to buy it twice. SPURIOUS (a task-specific instruction generalised into a standing rule) was 1/3 vs 0/3 — noise by the N=3 criterion, so no harm established either.
- **What that round did NOT test, and it is the half FEDERATION #7 is actually about**: the rule announced itself. A real standing rule usually arrives **implicitly** — as a correction, across several turns, or inferred from a reaction. That is how the two preferences currently sitting in this repo's private Claude Code `memory/` arrived. The protocol captures a standing rule that declares itself; whether it captures one that does not is **untested**, and the next round is that case, not a reworded section.

- **13.7's drift was a trigger failure, not a declarative one — and that distinction reopens the fix** (corrects the reading recorded above). §6's rule is *"update `03-code-map.md` … in the SAME response as any change"*: that is already the forced-same-response-write shape, the one measured at **7-8/8** on the glossary in Milestone 11, not the declarative shape measured at ~0. A procedural rule **in its strongest known form still missed**, so "phrase it procedurally" is not an available fix — it is already phrased that way. What failed was the trigger: `any change` did not register when the change was adding a development harness. Rewording the trigger patches one event and leaves the class intact: **any rule that depends on the agent classifying an event correctly fails the same way on the next unanticipated event.** The only fix that removes the class is one that asks the agent to notice nothing.

## Known issues
### AI forgets to pause
- **Symptom**: The AI ignores the "Handoff" rule and proceeds straight to execution.
- **Root cause**: Instruction tuning in some models prioritizes fulfilling the user's ultimate goal in one go.
- **Status**: Mitigated
- **Workaround**: Explicitly state "STOP" and "Wait for the user" in the prompt.

### Recency Bias causes Protocol Drift
- **Symptom**: During long sessions (15+ turns of intense technical work), the agent creates ad-hoc files in `.bemyagent/` instead of updating existing protocol files. The agent "knows" the protocol structure but doesn't consult it before acting.
- **Root cause**: In transformers, recent user instructions have disproportionate attention weight over rules read many turns ago. Declarative rules degrade to ~20-30% compliance after context truncation. Simple/familiar tasks are executed in "fast-path" mode with less deliberation, making them more vulnerable.
- **Status**: Mitigated (Decision 13 — Protocol Anchoring Gate)
- **Workaround**: Procedural gate with forced `PROTOCOL_CHECK:` output before any write to `.bemyagent/`.
